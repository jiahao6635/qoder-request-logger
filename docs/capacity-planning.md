## 2. 峰值流量估算

### 2.1 推导链

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 总用户 | 500 | 公司规模上限 |
| 同时活跃 | ~300 | 经验值：研发人群中约 60% 在工作时段开着 AI 编码助手 |
| 人均事件率 | 0.5~2 事件/s | 一轮"提示词 → 若干工具调用 → 响应 → Credits 汇总"被 hook 拆为多条记录（`USER_REQUEST`、`TOOL_REQUEST`、`TOOL_RESPONSE`、`LLM_USAGE`…），一次密集 agent 轮次可瞬时产生 5~10 条 |
| **峰值流量** | **150~600 条/s** | 300 × 0.5 ~ 300 × 2 |
| **设计容量** | **1000 条/s** | 相对典型负载（~300 条/s）约 **3 倍余量**，且覆盖峰值上限 600 条/s 后仍有 1.67 倍头部空间 |

### 2.2 流量形态（为什么余量是必要的）

| 特征 | 说明 |
| --- | --- |
| 潮汐性 | 上午 10~12 点、下午 14~17 点为高峰；午休/晚间回落一个数量级 |
| 突刺 | 单个多 agent 并行会话（QoderWork 长任务）可瞬时打出数十条/s；全员早高峰开机 `SessionStart` 同步潮 |
| 无重试放大（正常态） | 客户端 hook 每条记录单次 POST；仅失败才进 outbox 重试（`drainBatch` 200 条/次，有界） |
| 重试放大（异常态） | Server 停机恢复瞬间的 outbox drain 潮 ≈ 常态峰值 × 在线人数比例，设计容量 1000 条/s 同时覆盖此场景 |

## 3. 入口带宽

| 项目 | 计算 | 结果 |
| --- | --- | --- |
| 单条记录 | hook payload + 盖章字段，平均 | **~1.2 KB** |
| 峰值带宽 | 600 条/s × 1.2 KB | ≈ 0.72 MB/s |
| 设计带宽 | 1000 条/s × 1.2 KB | **< 1.2 MB/s** |
| 千兆内网容量 | 1000 Mbps ÷ 8 | 125 MB/s |
| **占比** | 1.2 ÷ 125 | **< 1%** |

结论：入口带宽不构成任何约束；即使未来流量 ×10，仍在单千兆链路承载范围内。

## 4. 服务端并发模型：Tomcat 200 线程足够

### 4.1 单请求处理画像

`POST /api/logs` 的处理路径全部为**短 CPU + 本地顺序 IO** 操作：

| 步骤 | 操作 | 量级 |
| --- | --- | --- |
| 1 | Tomcat 接收 + 反序列化 ~1.2KB JSON | < 0.5 ms |
| 2 | `X-API-Key` SHA-256 校验（36 字符，内存注册表哈希比对） | μs 级 |
| 3 | 去重判定（记录指纹 → 内存 LRU/布隆） | μs 级 |
| 4 | 盖章（`ingest_user`/`ingest_time`）+ 追加写 spool 段文件（buffered append） | < 1 ms（本地 SSD 顺序写） |
| **合计** | | **P99 < 5 ms** |

### 4.2 容量论证

| 推导 | 计算 | 结论 |
| --- | --- | --- |
| 理论吞吐 | 200 线程 × (1000 ms ÷ 5 ms/请求) | **40,000 条/s** |
| 保守有效吞吐（打 2~3 折：fsync、GC 停顿、锁竞争） | 8,000~20,000 条/s | 仍为设计容量的 **8~20 倍** |
| 磁盘瓶颈 | 顺序写 1.2 MB/s（设计容量）vs SSD 数百 MB/s | 磁盘余量两个数量级以上 |
| 客户端容忍度 | `QODER_LOG_HTTP_TIMEOUT_MS` 默认 5000ms；hook 侧 timeout 15~30s | 即使 P99 恶化到百毫秒级，客户端完全无感 |

### 4.3 结论：不需要 WebFlux / 内存队列

| 方案 | 评估 |
| --- | --- |
| **同步阻塞 + 追加写（选定）** | 代码最简、崩溃语义最清晰（收到即落盘，进程死不丢已确认数据）；容量余量 8 倍以上 |
| WebFlux/响应式 | 吞吐收益在万级 RPS 才显现；调试与运维复杂度不匹配本场景 |
| 内存队列 + 异步刷盘 | 引入"确认了但没落盘"的丢数据窗口，与审计场景的**抗抵赖**要求冲突 |

## 5. JVM 与 VM 规格

| 项目 | 取值 | 论证 |
| --- | --- | --- |
| 堆 | **2~4 GB**，生产 `-Xms1g -Xmx3g` 起步 | 常驻大对象：Key 注册表（500 条目 × ~200B，可忽略）+ 去重窗口 + spool 写缓冲 + Tomcat 200 连接的请求缓冲（200 × ~4KB ≈ 1MB）。真正吃内存的是突发 in-flight 请求与 GC 年轻代余量，3GB 堆绰绰有余 |
| GC | **G1GC**（`-XX:+UseG1GC`） | 中等堆 + 低停顿目标（审计写入路径无 STW 敏感业务，但 G1 在 4GB 下的停顿表现稳健、无需调参） |
| VM 规格 | **4C8G 起步** | 4 核：1000 条/s × ~2ms CPU ≈ 2 核占用，双核余量；8G：3GB 堆 + 堆外/元空间/页缓存 ≈ 6~7GB |
| 升级触发 | CPU 持续 > 60% 或 GC 停顿 > 200ms | 先纵向升 8C16G（成本低、无架构动作），再考虑 §8 水平扩展 |

## 6. 磁盘规划：100GB spool

| 推导 | 计算 |
| --- | --- |
| 日均未压缩全量 | 按潮汐曲线均摊 ~100 条/s × 86,400s ≈ 860 万条/天 × 1.2KB ≈ **~10 GB/天** |
| spool 正常态 | 分钟级滚动 + 即时上传成功后删除，稳态占用 **< 1 GB** |
| OSS 断链兜底 | 100GB ÷ 10GB/天 = **10 天**未压缩全量缓冲（叠加客户端本地双写 + 8MB outbox，双层兜底） |
| 告警线 | 80% 告警、90% 返回 503 劝退客户端（见 `runbook.md` §6.2） |

规划要点：spool 独立数据盘挂载（防系统盘写满拖垮整机）；SSD/ESSD（顺序写带宽与 fsync 延迟均远超需求，PL0 即可）。

## 7. OSS 存储与成本估算

### 7.1 日增量

| 项目 | 计算 | 结果 |
| --- | --- | --- |
| 未压缩 | ~10 GB/天 | — |
| gzip 压缩比 | 8~12×（JSONL 字段名重复率高） | — |
| **压缩后日增** | 10GB ÷ 8 ~ 10GB ÷ 12，含 `_manifest` 与对象元数据开销 | **1~1.5 GB/天** |
| 对象数 | 见 `oss-path-spec.md` §11（数千对象/天，ListObjects 无压力） | — |

### 7.2 生命周期下的留存体积与成本随时间变化

生命周期规则（`runbook.md` §1.1）：0~180 天标准存储，181~365 天转 IA，365 天后删除。以日增 **1.25 GB（中位）** 估算：

| 时间点 | 标准存储 | IA 存储 | 留存总体积 | 月存储成本估算* |
| --- | --- | --- | --- | --- |
| 第 30 天 | 37.5 GB | 0 | 37.5 GB | ≈ ¥4.5 |
| 第 180 天 | 225 GB | 0 | 225 GB | ≈ ¥27 |
| 第 365 天 | 224 GB | 231 GB | **455 GB（峰值）** | ≈ ¥45 |
| 第 366 天起（稳态） | 224 GB | 231 GB | **稳定 ≈ 455 GB**（每日新增 1.25GB 进、最老 1.25GB 删除） | **≈ ¥45/月** |

\* 单价按 OSS 本地冗余标准 ≈ ¥0.12/GB/月、低频 IA ≈ ¥0.08/GB/月 估算，实际以当期官网价格与地域为准；请求费用忽略不计（日请求量万级，远低于免费额度）。

| 结论 | 说明 |
| --- | --- |
| 存储成本可忽略 | 稳态月成本 **数十元级**，不构成任何架构决策因素 |
| 带宽费用 | Server 与 Bucket 同地域走内网 Endpoint，上传零流量费；审计下载 1~1.5GB/天全量拉取也仅在使用外网时产生费用 |
| 峰值留存 | 365 天全量审计窗口 ≈ **0.5 TB**，为容量规划（Bucket 配额/告警）的唯一长期约束 |

## 8. 水平扩展演进路线

### 8.1 路线图

| 规模 | 方案 | 协调成本 |
| --- | --- | --- |
| ≤ 1000 人 | **单实例**（4C8G） | 零。§4 论证单实例即有 8 倍吞吐余量，1000 人峰值 ≈ 1200 条/s 仍在其能力带内 |
| 1000 ~ 5000 人 | **加第二实例：Nginx / DNS 轮询** | **零协调**（关键论证见 8.2） |
| > 5000 人 | 届时再评估**一致性哈希**按 user 分片路由 | **当前明确不推荐**：协调成本（一致性哈希环、成员发现、再平衡迁移）与收益不成比例——本系统无跨用户查询一致性要求、无跨实例事务、OSS 天然按 user 分区 |

### 8.2 为什么多实例轮询是"零协调"的

这是本架构的关键性质，由三个设计决定共同保证：

| 设计决定 | 多实例下的效果 |
| --- | --- |
| ① 记录无状态：每条 `POST /api/logs` 独立、幂等，无会话粘性需求 | Nginx 轮询/最少连接随便分发，同一客户端的请求落不同实例无任何副作用 |
| ② part 文件名含**实例 ID 段**（`part-<HHmmss>-<实例ID 4hex>-<序号>`，见 `oss-path-spec.md` §7.1） | 两实例并发写同一 `date=/user=/src=` 前缀**天然无路径冲突**，无需任何分布式锁或分配器 |
| ③ `api-keys.yml` 为只读共享配置（同一份分发到各实例，均热加载） | 任意实例都能校验任意 Key 并盖出相同的 `ingest_user`，路由到哪个实例归因结果一致 |

唯一实例间差异是各自的 spool 与指标；`_manifest` 由**指定主实例**（或加简单 Leader 锁/定时任务单节点部署）在 02:00 生成，遍历前缀聚合——manifest 是对 OSS 只读扫描，单点生成无可用性风险。

> 换算：5000 人 × 60% 活跃 × 2 事件/s ≈ 6000 条/s 峰值。届时按 §5 先纵向（8C16G ≈ 双倍吞吐），两台 8C16G 轮询即覆盖 ~16000 条/s 有效吞吐——**一致性哈希在可预见规模内没有出场必要**。

### 8.3 扩容操作（运维侧）

```bash
# 第二实例上线三步（无停机、无数据迁移）：
# 1) 同一份 api-keys.yml 分发到新机
# 2) 同一 OSS_AK_ID/OSS_AK_SECRET（writer 账号对前缀有写权限，天然共享目标）
# 3) Nginx upstream 加入新节点（或 DNS 加 A 记录），客户端零改动
```

## 9. 压测验证建议（上线前执行一次）

| # | 场景 | 方法 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 常态吞吐 | 压测机对 `/api/logs` 持续灌 300 条/s × 30min（样例记录取自真实 `requests_<D>.jsonl`） | P99 < 20ms，CPU < 30%，spool 稳态 < 1GB |
| 2 | 峰值+突发 | 1000 条/s × 10min，叠加 2000 条/s × 60s 突刺 | 无 5xx；GC 停顿 < 200ms；`upload.lag` 突刺后 5min 内回落 |
| 3 | OSS 断链演练 | 临时用错误 endpoint，灌 100 条/s × 10min 后恢复 | spool 线性增长符合 §6 速率；恢复后自动排空，`oss-reconcile.js` 零差异 |
| 4 | 优雅停机 | 峰值灌入中 `systemctl restart` | 120s 内退出；重启后数据续传无丢失 |
| 5 | 联调桩比对 | `node tools/mock-log-server.js --port 18080 --out ./mock-out` 与生产 Server 同源灌数 | 两者产出的 JSONL 逐字段一致（含 `ingest_user`/`ingest_time` 盖章） |

> 压测记录与结果归档至 `reports/`（沿用 `e2e-acceptance-2026-09-01.md` 的验收风格：结论/级别/说明 检查表 + 指标表格）。
